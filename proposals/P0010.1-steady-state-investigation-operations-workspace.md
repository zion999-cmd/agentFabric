# P0010.1: Steady-State Investigation & Operations Workspace

**Status**: Proposed
**Date**: 2026-08-21
**Depends on**: P0010

## Objective

P0010 已证明 Agent 能从 Situation 出发，读取专业 Knowledge，判断“自己还需要知道什么”，通过 Fabric Capability 获取额外 Evidence，更新 Hypothesis，并形成 Judgment / StopReason。

P0010.1 不创造新的推理架构，而是把这一能力从“人工触发的 Investigation Demo”提升为 Agent Runtime 的 steady-state 正常行为：数据持续进入 Fabric，新 Situation 出现后 Agent 自动开始调查，并把调查过程、当前理解和最终建议作为 Workspace 的主要业务表象。

本阶段结束后，Workspace 不应再主要表现为 Ranking / Signal / BI 告警列表，而应让专业人员直接看到：Agent 发现了什么、正在调查什么、已经确认什么、还不知道什么、为什么这么判断，以及最终建议怎么处理。

本阶段止于 Recommendation。Agent 不执行外部业务 Action。

---

## Background

### 1. P0010 已经解决了“Agent 是否知道自己该问什么”

当前 canonical investigation path 已经成立：

Situation
→ Hermes Session
→ Knowledge
→ Known Evidence
→ Hypotheses
→ Next Question
→ Required Evidence
→ Fabric Capability
→ New Evidence
→ Findings
→ Judgment
→ StopReason

真实业务验证已经证明 Agent 可以：

- 识别周度节律、小样本等伪异常；
- 在证据充分时停止继续 Acquisition；
- 同时维护多个竞争 Hypothesis；
- 选择信息增益较高的 Next Question；
- 主动调用已有 Fabric Capability 补证据；
- 识别 Fabric 无法获取的证据并暴露能力边界；
- 在不应该干预时输出 observe，而不是机械“发现异常就优化”。

因此 P0010.1 不重新解决 reasoning 问题。

### 2. 当前 Runtime 与 Workspace 表象脱节

当前 Runtime 已经能够 Investigation，但 Workspace 仍保留较强的旧产品语义：

- 首页主要展示 Ranking / Signal；
- Situation 仍需要人工点击“交给 Agent 调查”；
- Current Understanding 只是 Detail 中的一块内容；
- Investigation Track 没有成为一等业务表象；
- Evidence Viewer 面向 Capability / Evidence Store，而不是运营人员理解的“为什么这么判断”；
- Judgment 后仍连接旧的“认同 / 判断错了 / 采用建议 / 不采用 / 稍后处理”等 Intervention UI。

结果是：

Runtime 已经开始像运营人员工作，
Workspace 仍然像 BI + Ranking 告警系统。

### 3. 数据进入 Runtime 仍缺 steady-state 入口

当前 Acquisition 主要服务于：

- startup/backfill；
- Investigation 中 Agent 主动补证据；
- 手工/开发验证。

但持续运营要求 Fabric 能按照配置周期获取基础业务数据。

因此需要补一个最小 Scheduled Acquisition，使已有 Capability 可以按固定 schedule / cron 持续产生 Evidence。

Scheduled Acquisition 不负责业务判断。

### 4. Judgment 还没有自然下游

P0010 最终能够回答：

“Agent 现在认为发生了什么？”

但专业运营还需要下一句：

“所以你建议怎么办？”

因此 P0010.1 增加 Recommendation，但 Recommendation 必须来自 Investigation / Judgment，而不是从 Signal、Ranking 或单个指标直接生成。

## Design

### 1. Scheduled Acquisition

增加最小 Scheduled Acquisition 配置能力。

目标不是建立 Scheduler Engine，而是允许已有 Fabric Capability 定期执行。

概念结构：

ScheduledAcquisition
- id
- capability
- schedule
- enabled
- lastRunAt
- lastStatus

初期 schedule 可以直接使用 cron expression 或项目已有 scheduling primitive。

示例语义：

trade.overview
→ 每天固定时间采集

traffic.overview
→ 每天固定时间采集

product.overview
→ 每天固定时间采集

执行路径必须复用现有：

Fabric Capability
→ Acquisition
→ Evidence Store

不得建立第二套 acquisition implementation。

#### Scheduled vs Agent-directed Acquisition

必须明确区分：

Scheduled Acquisition
= Fabric 根据配置持续观察世界

Agent-directed Acquisition
= Investigation 为回答某个具体问题主动补证据

两者最终都进入同一个 Evidence Store。

Scheduler 不产生 Judgment、Hypothesis 或 Recommendation。

---

### 2. Automatic Investigation Lifecycle

当前“交给 Agent 调查”属于 P0010 acceptance trigger，不应继续作为正常业务生命周期入口。

steady-state 应变为：

New Situation
→ 自动创建/复用 Situation Hermes Session
→ 自动启动 P0010 Investigation
→ 持久化 investigation
→ Workspace 更新

必须 REUSE P0010 已有：

- situation Hermes session；
- investigation prompt contract；
- Knowledge routing；
- fabric_execute_capability；
- LearningContext.investigation；
- contract extraction；
- timeout / honest degradation。

不得建立新的 Agent、Planner、Question Engine 或 Investigation Engine。

#### Manual trigger

原“交给 Agent 调查”可以：

- 删除；或
- 降级为 retry / developer control。

但不得继续成为正常业务流程的必要步骤。

---

### 3. Workspace Information Architecture

Workspace 从“Signal / Ranking 告警中心”调整为“Agent Operations Workspace”。

这不是视觉 redesign，而是信息优先级调整。

#### Situation List / 今日工作

Situation 列表至少应让用户直接识别：

- What happened；
- Agent 当前状态；
- Current Judgment；
- 是否 observe；
- 是否仍在 investigation；
- 是否存在 missing evidence / human boundary；
- 是否已经产生 Recommendation。

不要求用户进入 Detail 才知道 Agent 到底怎么看。

列表不应继续以 Ranking score 作为主要业务意义。

Ranking 可以作为 Situation 来源或 supporting signal，但不能替代 Agent Understanding。

---

### 4. Current Understanding

Current Understanding 表示：

“Agent 现在怎么看这件事情。”

它是 Investigation 的 current snapshot，不是 Track。

继续 REUSE：

LearningContext.investigation

至少表达：

- Judgment；
- Findings；
- Known Evidence；
- Hypotheses；
- Unknowns；
- Next Question / Observe；
- Capability Boundary；
- StopReason。

不得调用 LLM 做 UI rendering。

不得建立第二套 Understanding persistence。

---

### 5. Investigation Track

新增一等业务表象：

Investigation Track

它回答：

“Agent 是怎样一步一步走到这个判断的？”

Track 是业务可审计过程，不是 Chain-of-Thought。

允许展示的对象是已经结构化、可持久化的业务事件，例如：

- Situation detected；
- Question asked；
- Hypothesis proposed；
- Evidence requested；
- Capability invoked；
- Evidence received；
- Finding established；
- Hypothesis supported / weakened / rejected；
- Missing capability identified；
- Judgment formed；
- Investigation stopped。

示例：

09:03 发现
订单量较基准明显下降

09:03 调查问题
需要先排除周度节律

09:04 获取证据
trade.overview

09:04 发现
与上周同日相比订单下降 82.5%

09:05 假设更新
“正常周末节律” weakened

09:05 下一问题
需要确认付费流量是否异常

09:06 能力边界
Fabric 当前无法获取京准通账户状态

09:06 判断
较大概率为真实流量异常，需要人工核验

Track 不保存或展示模型内部 Chain-of-Thought。

如果 P0010 当前持久化结构不足以重建业务 Track，允许对 investigation contract 做最小增量扩展，但必须先 audit 现有字段能否 REUSE。

不得新建独立 Reasoning Trace 系统。

---

### 6. Track 与 Evidence 的关系

必须严格区分：

Investigation Track
= Agent 如何调查

Evidence
= 某一步调查使用了什么事实

Evidence Store
= 事实的底层 provenance / acquisition record

关系：

Investigation Track
        ↓
Evidence Reference
        ↓
Evidence Store

运营人员点击：

“为什么这么判断？”

首先进入 Investigation Track。

如果需要进一步核验某一事实，可以从 Track 下钻到对应 Evidence。

现有：

Advanced → Evidence

继续保留，定位为开发 / 审计 / provenance 工具。

不得把 Evidence Viewer 改造成第二套 Investigation UI。

---

### 7. Recommendation

Recommendation 是 P0010.1 的终点。

严格数据流：

Investigation
→ Judgment
→ Recommendation

禁止：

Signal → Recommendation

Ranking → Recommendation

Metric threshold → Recommendation

Recommendation 必须建立在 Agent 已形成的 Judgment 上。

Recommendation 至少表达：

- recommendation；
- rationale / linked judgment；
- expected outcome；
- known risks / uncertainty；
- prerequisites；
- human-needed information（如有）。

具体 schema 应优先扩展现有 Learning Context / investigation contract，而不是立即建立新的 Recommendation subsystem。

实现前先 audit 当前 Intervention / LearningContext schema，优先 REUSE / REPAIR。

---

### 8. Human Boundary

P0010.1 只需要正确表现“什么时候需要人”，不建立完整 Action Approval System。

本阶段至少区分：

#### A. Missing Capability / Missing Information

Agent 需要的信息 Fabric 无法获得：

Agent
→ Recommendation / Human Request

例如：

- 京准通账户状态；
- 实际库存；
- 差评内容；
- 平台小二沟通结果。

Workspace 应明确显示：

“需要人工核验”

而不是把 unknown 包装成答案。

#### B. Recommendation Feedback

用户可以对 Recommendation 表达业务反馈。

本阶段反馈的目的仅是：

- 记录 recommendation 是否被接受；
- 记录 correction / additional context；
- 为未来 Experience / Skill Evolution 保留真实反馈。

本阶段不实现 Skill 更新。

#### C. External Action Approval

仅定义为未来边界。

如果未来 Fabric Capability 能修改外部系统：

Recommendation
→ Action Proposal
→ Approval
→ Execute

本阶段不实现。

#### D. Long-running Authorization

持续广告调整、长期库存策略、持续价格操作等需要独立 Policy / Authorization。

本阶段不实现。

---

### 9. Existing Intervention UI

当前：

Agent 判断
- 认同
- 这里判断错了
- 还有一个你不知道的情况

Agent 建议
- 采用建议
- 不采用
- 稍后处理

你准备怎么处理？
- 我准备这样处理
- 暂不处理

不能直接作为未来 Interaction Model 保留。

实施前应 audit：

- 哪些数据已经进入 Learning Context；
- 哪些是真实 consumer；
- 哪些只是旧 UI；
- 哪些可以映射到 Recommendation Feedback；
- 哪些属于未来 Action / Approval。

按 REUSE / REPAIR / REMOVE 分类。

不得为了兼容旧 UI 同时维护两套 interaction grammar。

---

### 10. Ranking Explainability

Ranking Explainability 已经完成真实 E2E，但产品层级需要降低。

它属于：

Ranking
→ Explainability / Trust
→ Supporting Trace

不是 Situation 的主要业务解释。

在业务 Workspace 中：

Current Understanding / Investigation Track

优先于：

Ranking Explainability

Ranking Trace 应作为 secondary drill-down。

不得删除现有真实 Trace 能力。

不得重新计算 trust。

## State Model

Workspace 应能从已有持久化事实推导 Situation 的业务状态。

建议语义状态：

uninvestigated
investigating
observing
judgment_ready
needs_human
recommendation_ready

这些首先是产品语义，不要求建立新的大型 state machine。

优先从：

Situation
+ LearningContext.investigation
+ Recommendation

派生。

如果必须持久化新增状态，应保持最小化并说明原因。

## Implementation Sequence

### Slice 0 — Wiring Audit

只读。

确认：

1. Situation 当前在哪里产生；
2. 哪个事件可以安全触发 automatic Investigation；
3. P0010 investigation session / lifecycle 的真实入口；
4. LearningContext.investigation 当前完整 schema；
5. 是否已有足够字段重建 Investigation Track；
6. 旧 Intervention UI producer / persistence / consumer；
7. Recommendation 是否已有可复用字段；
8. 当前 Acquisition 是否已有 scheduler / timer primitive；
9. Workspace Situation List 的真实 data source；
10. Ranking Explainability 当前 UI coupling。

输出 REUSE / WIRE / REPAIR / REMOVE / MISSING。

出现 schema gap 时停止，不猜。

### Slice 1 — Workspace Investigation Surface

先让产品表象追上 P0010：

- Situation list Agent status；
- Current Understanding；
- Investigation Track；
- Evidence drill-down；
- Ranking Explainability secondary 化。

此 Slice 不新增 Recommendation reasoning。

### Slice 2 — Automatic Investigation

把 P0010 从人工按钮触发改为 Situation steady-state 自动触发。

验收重点：

新 Situation
→ 无人工点击
→ Hermes Investigation
→ LearningContext persistence
→ Workspace 更新

保留诚实 timeout / failure。

### Slice 3 — Scheduled Acquisition

为已有 capability 增加最小 schedule 配置。

验收：

schedule 到点
→ existing Fabric capability
→ real Evidence
→ existing Situation path

Scheduler 不做业务判断。

### Slice 4 — Recommendation

基于 persisted Judgment 让 Agent 形成 Recommendation。

验收：

Investigation
→ Judgment
→ Recommendation
→ Workspace

Recommendation 必须能追溯 Judgment / Track。

### Slice 5 — Human Feedback

只实现 Recommendation 反馈：

- accept；
- reject；
- correction / additional context。

反馈进入现有 Learning Context / canonical experience path。

不得触发外部 Action。

## Success Criteria

1. 新 Situation 出现后，无需人工点击“交给 Agent 调查”，Agent 能自动启动 P0010 Investigation。

2. Agent Investigation 继续真实读取 knowledge/，而不是 Fabric 复制 SOP 或硬编码调查树。

3. Agent 在需要额外数据时继续通过现有 Fabric Capability 获取 Evidence。

4. Workspace 首页不再只能看到 Ranking / Signal，而能直接判断 Situation 当前处于：
   - investigating；
   - observing；
   - judgment ready；
   - needs human；
   - recommendation ready。

5. Situation Detail 明确区分：
   - Current Understanding = NOW；
   - Investigation Track = HOW。

6. Investigation Track 展示结构化业务调查事件，但不保存或暴露 Chain-of-Thought。

7. Track 中使用的 Evidence 可以继续下钻到底层 Evidence provenance。

8. Advanced Evidence Viewer 继续可用，不承担业务 Investigation 主表象。

9. observe 案例不会伪造“下一步调查”或 Recommendation urgency。

10. missing capability 案例明确显示“需要人工核验”，不会把 unknown 包装成事实。

11. Recommendation 只从 Investigation / Judgment 产生，不直接从 Signal / Ranking / threshold 产生。

12. Recommendation 能在 Workspace 中被专业人员理解，并可追溯其 Judgment / Evidence。

13. 用户可以对 Recommendation 做最小 accept / reject / correction 反馈，且反馈进入 canonical Learning Context / experience path。

14. Scheduled Acquisition 能配置至少一个已有 capability 按固定时间执行，并产生真实 Evidence。

15. Scheduled Acquisition 与 Agent-directed Acquisition 共用现有 Fabric acquisition / Evidence path，不存在第二套数据获取实现。

16. Ranking Explainability 保持真实 E2E，但在业务 Workspace 中成为 secondary drill-down。

17. 不产生任何未经人工授权的外部业务修改。

18. 浏览器 Acceptance 必须能肉眼验证至少三种真实业务状态：

   A. 伪异常
   Situation
   → Automatic Investigation
   → Track
   → observe
   → 不建议干预

   B. 真异常但 Fabric 缺证据
   Situation
   → Investigation
   → competing hypotheses
   → capability boundary
   → needs human
   → Recommendation

   C. 证据充分
   Situation
   → Investigation
   → Judgment
   → Recommendation
   → Human feedback

19. Workspace reload 后 Understanding / Track / Recommendation 状态仍然存在，不依赖前端内存。

20. P0010 原有 behavioral acceptance 不回归。
