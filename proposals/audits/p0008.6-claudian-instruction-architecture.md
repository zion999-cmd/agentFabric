# P0008.6 Audit — Fabric Workspace Instruction Architecture

**Date**: 2026-08-14
**Type**: Architecture archaeology / audit — NOT implementation
**Inputs**: Claudian source (`/tmp/claudian-arch`, GitHub `YishenTu/claudian`), P0008.5 全证据链, P0008.4 Claudian–Hermes Gap, `data/fabric-workspace/` 现状

---

## 0. 结论先行（供 Review 快速判断）

1. **Claudian 的 Instruction Architecture 核心不是"AGENTS.md 写得有多好"，而是"指令分成三层、各自归谁、谁加载谁"**。这个分层是 agentFabric 真正该继承的东西，而不是某个具体文案。

2. **P0008.5 的 World 消费失败，根因不是"少一行"**，而是 Instruction Architecture 里 **`world/`（systems/）从来没有 READ-side（消费侧）指令**——它只有 WRITE-side（构建侧）指令。`knowledge/` 之所以成功，是因为它偶然同时拥有两侧指令。

3. **Proposed 结构（Part C）方向正确但有一处冗余（`knowledge/AGENTS.md` + `knowledge/KNOWLEDGE.md` 双指令）和一处致命缺失（无 Routing 规则 + 无 Epistemic Semantics）**。结构不是答案，Routing + Epistemic Semantics 才是。

4. **四个已验证行为里，没有任何一个是 Runtime Skill 或 Fabric Capability**。它们全部是 Workspace Instruction + Navigation + Fabric Procedure。真正的"防退化"手段是让它们持久化为 workspace 内的指令/程序/地图文件，而不是停留在测试报告里。

## 1. Claudian Archaeology

> 方法：只读 `/tmp/claudian-arch`（`git clone --depth 1`），只看 Agent Instruction / Context Environment 相关文件。忽略 UI、Obsidian plugin 实现、CSS、ESBuild 配置。

### 1.1 Instruction Hierarchy — Claudian 有 **三条独立的指令轨道**

Claudian 最关键的发现不是"它有一个 root AGENTS.md + 一堆 scoped AGENTS.md"，而是**它把指令明确拆成三条互不混淆的轨道，每条轨道的"受众"不同**：

| 轨道 | 载体 | 受众 | 加载方式 |
|------|------|------|----------|
| **A. Repository developer instruction** | root `AGENTS.md` + 9 个 scoped `AGENTS.md`（`src/app/`、`src/core/`、`src/features/chat/`、`src/providers/{claude,codex,grok,opencode,pi}`、`src/style/`） | **编辑 Claudian 源码的开发者** | provider CLI 从 cwd 原生加载 root AGENTS.md；scoped 由 root 的 "Scope Guides" 指向、按需读取 |
| **B. Runtime system prompt** | `src/core/prompt/mainAgent.ts` 的 `buildSystemPrompt()` → `Options.systemPrompt` | **在 Obsidian vault 里工作的终端用户 agent** | Claudian 代码注入 system prompt，非文件 |
| **C. User's vault instruction** | vault 内用户自己的 `AGENTS.md` / `CLAUDE.md` | **终端用户 agent** | provider CLI 原生发现（Claudian 设 `cwd = vault root`，自己绝不读写） |

**三个关键结构事实**：

1. **`CLAUDE.md` = `@AGENTS.md`**（root 的 `CLAUDE.md` 全文就是 `@AGENTS.md`）。每个 scoped 目录也有 `CLAUDE.md`，同样是指针。规则原文（root AGENTS.md line 29）：
   > `CLAUDE.md` files should import the nearest `AGENTS.md`; do not duplicate shared guidance there.

   即：**CLAUDE.md 是 AGENTS.md 的导入指针，绝不复制内容**。这是为了兼容多个 provider 各自的入口文件名（Claude Code 读 CLAUDE.md，Hermes 读 AGENTS.md/CLAUDE.md/HERMES.md），但内容只存一份。

2. **scoped AGENTS.md 由 root 的 "Scope Guides" 清单 + 一条规则组织**（root AGENTS.md line 11-25）：
   > Before editing a scoped area, read its nearest scoped guide: `src/app/AGENTS.md` …（列出 9 个）
   > Keep repository-wide rules here; put local ownership, dependencies, invariants, failure modes, verification, and active decisions in the narrowest scoped guide that governs them.
   > Do not duplicate inherited guidance or silently contradict it.

   即：**root 负责"仓库级规则 + 指向 scoped 的索引"，scoped 负责"该 scope 特有的 ownership / invariant / gotcha"**。scoped 不是自动加载的，而是"进入该区域时按规则去读"。

3. **system prompt（Track B）的组装顺序**（`mainAgent.ts:buildSystemPrompt`）：
   ```
   User Context (userName)
   → Time Context
   → Identity & Role ("You are Claudian… operating in the user's Obsidian vault… cwd = vault root")
   → Path Conventions (Vault=relative / External=absolute)
   → User Message Format (context tag 语法)
   → Obsidian Context (Markdown/frontmatter/wikilink/tag 内容模型)
   → Selection Context
   → Image Instructions
   → Custom Instructions (用户自己的 customPrompt，最后追加)
   ```

   `ClaudeExecutionRequestEncoder.ts:134` 显示：Claudian 只在 `systemInstructions.kind === 'explicit'` 时走自定义指令，否则用 `buildSystemPrompt` 拼装；而 `cwd: sessionConfig.vaultWorkingDirectory`（line 150）才是让 provider CLI 原生读到 vault AGENTS.md 的关键。

### 1.2 Workspace Orientation — orientation 不在 AGENTS.md 里，在 system prompt 里

这是对 agentFabric 最重要的一个反直觉发现。

Claudian 的 AGENTS.md 是**给开发者**的（"如何正确编辑 Claudian 源码"）。而**给终端用户 agent 的 orientation**（"我在哪、这是什么、怎么导航、什么能改"）**全部在 `buildSystemPrompt()` 里**：

- **我在哪**：`"The current working directory is the user's vault root."` + `vaultPath`
- **内容模型是什么**：`"Obsidian Context"` —— Markdown、YAML frontmatter、wiki-link `[[note]]`、`#tag`、Dataview、`.obsidian/` 配置
- **怎么导航**：`"Path Conventions"` 表（vault 相对路径 vs external 绝对路径）+ 内容模型（wikilink 互链）
- **什么能改**：`"Safety First: You never overwrite data without understanding context."` + path rules（相对路径规则）

agentFabric 与 Claudian 的处境是**镜像相反**的：

- Claudian **有** runtime（自己写 system prompt），所以 orientation 能注入 system prompt。
- agentFabric **没有** runtime（Hermes 是 runtime），所以 orientation **不能注入 system prompt，只能放进 Hermes 原生从 cwd 加载的那个文件**——也就是 **workspace root 的 `AGENTS.md`**。

这正是 P0008.4 已经得出的结论。本 Audit 在此基础上确认：**agentFabric 的"workspace root AGENTS.md"承担的是 Claudian 的 Track B（system prompt）角色，而不是 Track A（repo AGENTS.md）角色**。这个角色认知错了，就会写出"讲结构但不讲怎么消费"的 AGENTS.md——而 P0008.5 恰恰证明了这点。

### 1.3 Context Routing — Claudian **没有 router，也没有 INDEX**

明确回答任务 Part A Q3：**Claudian 不存在显式的 question/task → instruction → 选择 context → navigation → content 的 router。**

Claudian 的"routing"是**涌现式**的，由三样东西拼起来：

1. `cwd = vault root`（工作目录即内容根）
2. provider 原生 file tools（Glob / Grep / Read / LS）—— agent 自己 grep 找
3. system prompt 教的**内容模型**（Markdown + wikilink + tag）—— 让 agent 知道"该 grep 什么、读了 A 要不要顺着 `[[B]]` 读 B"

外加一套**显式 context passing**（不是 router，是用户/编辑器主动喂上下文）：`@file.md`、`<linked_note>`、`<editor_selection>`、`<context_files>` 等 tag。

**结论**：Claudian 的导航是"**教内容模型 + 给文件工具 + 让 agent 自己 grep**"，它没有预索引、没有 INDEX、没有 router。这意味着：**agentFabric 的 INDEX.md（Navigation Map）不是从 Claudian 学来的——Claudian 根本没有这个东西**。INDEX.md 是 agentFabric 在 P0008.5 里自己发现"结构化多文件目录需要显式导航入口"之后发明的。这一点必须说清楚，避免把 INDEX 误归因到 Claudian。

### 1.4 Scoped Instructions — 为什么不用一个巨大 root prompt

Claudian 的答案在 root AGENTS.md 的维护规则里，三条：

1. **局部性（locality）**：`put local ownership, dependencies, invariants, failure modes … in the narrowest scoped guide that governs them.` —— 局部规则放在它治理的代码旁边，读代码的人（agent）自然就近读到。
2. **root 瘦身**：仓库级规则（naming / TDD / dependency direction / review checks）才进 root，局部的 invariant/gotcha 不进 root，否则 root 膨胀成没人读的大文件。
3. **不重复、不矛盾**：`Do not duplicate inherited guidance or silently contradict it. State a necessary local exception and its rationale explicitly.` —— scoped 只写"与 root 不同或 root 没有的东西"，继承的规则不复制。

还有一个隐含的**作用域机制**：scoped AGENTS.md **不是自动加载的**，而是靠 root 的一条行为规则"进入某区域前先读最近 scoped guide"来触发。这意味着 **scoped 文件的存在依赖 root 的"指向 + 触发规则"**——没有指向，scoped 文件就是死文件（P0008.5 的 world/INDEX.md 已经用实验证明了"有文件但无指向 = 从不被读"）。

### 1.5 Boundaries / Permissions — Claudian 严格区分 Instruction Policy vs Runtime Enforcement

Claudian 的 AGENTS.md 里大量"只读""不允许 import"是**文字策略（Instruction Policy）**，不是安全机制。真正的 enforcement 全部是 provider/runtime 机制：

| 文字策略（AGENTS.md 说） | 实际 enforcement（代码做） |
|--------------------------|---------------------------|
| "world 只读" 类规则 | `cwd` + `additionalDirectories`（路径授权）、provider 原生 permission mode |
| "provider transcript 只读" | `permissionMode`（yolo/plan/safeMode）→ SDK `bypassPermissions/plan/default` |
| "不要 import provider 代码进 feature" | `canUseTool`（逐 tool 审批）、`disallowedTools`（禁用 subagent/tool） |
| "只 merge 不 replace settings" | `CCSettingsStorage.save()` merge 逻辑 + `settingSources` |
| "MCP 归 Claude Code" | Claudian 代码里**明确不碰** `.claude/mcp.json`（`src/providers/claude/AGENTS.md` Storage Rules） |

最干净的一条边界声明在 `src/providers/grok/AGENTS.md`（这是**本 Audit 最重要的单段原文**）：

> ## Repository Instructions vs Runtime Instructions
> - This `AGENTS.md` is a repository developer guide for contributors editing Claudian's Grok adapter.
> - Vault/runtime `AGENTS.md` files belong to the user and are discovered natively by Grok.
> - Claudian must never create, import, append, suppress, rewrite, or explicitly inject vault/runtime `AGENTS.md` files.

这段话把 Claudian 的 ownership boundary 一句话说清了：**Claudian 自己的 repo 指令 ≠ 用户的 vault/runtime 指令，Claudian 绝不碰后者。** 这正是 agentFabric "Fabric-owned instruction vs Runtime-owned instruction" 边界的最强先例。

### 1.6 Provider-Native Delegation — Claudian 明确"不重实现"的清单

从 AGENTS.md 的 "Provider Rules" 与各 provider scoped guide 归纳，Claudian **显式委托给 provider CLI、自己不重实现**的能力：

| 能力 | Claudian 动作 | 证据 |
|------|--------------|------|
| AGENTS.md/CLAUDE.md 加载 | 设 `cwd = vault root`，让 provider CLI 原生读 | `ClaudeExecutionRequestEncoder.ts:150` |
| filesystem tools（Read/Write/Edit/Glob/Grep/LS/Bash） | 不重实现 | P0008.4 已追踪 |
| 权限 / approval | `permissionMode` + `canUseTool` + provider 原生 approval gate（Codex `serverRequest`、OpenCode file permission） | `ClaudeExecutionRequestEncoder.ts:128-171` |
| session / transcript | provider 原生 JSONL；Claudian 只做 `.claudian/sessions` 元数据 bookkeeping | `src/providers/*/history/` 均 read-only |
| MCP 配置/认证/健康检查 | 归 Claude Code，Claudian 不碰 `.claude/mcp.json` | `src/providers/claude/AGENTS.md` Storage Rules |
| skills | provider 原生发现（Codex `skills/list`）；Claudian 的 `AgentSkillRepository` 只是 codec/validation 包装，不是重实现 | `src/core/skills/` |
| model/command/plan/subagent/memory | 全 provider-specific，core contract 不共享则不做 | root AGENTS.md "Provider Rules" |

核心原则（root AGENTS.md line 121）：
> Prefer provider-native behavior over local reimplementation. Adapt provider output at the boundary instead of shadowing provider features.

| Claudian Pattern | agentFabric Equivalent | 判定 | 理由 |

| Track A root `AGENTS.md`（repo-wide 规则 + Scope Guides 索引） | workspace-root `AGENTS.md` 的 "Scope Guides / routing rules" 段 | **ADAPT** | 语义从"代码 ownership"换成"context source routing"，但"root 只放全局规则 + 指向 scoped"的结构直接继承。 |

| 内容模型驱动的涌现式导航（grep + wikilink） | `INDEX.md` Navigation Map | **ADAPT（扩展）** | agentFabric 发现：结构化多文件目录（world/）靠 grep 不够，需要显式 INDEX；但 INDEX 必须配 routing 指针（见 §3）。这是对 Claudian 的**补强**，不是照搬。 |
| "Repository vs Runtime Instructions" 边界声明 | Fabric-owned vs Runtime-owned 边界 | **REUSE（原则）** | 直接继承"绝不创建/注入/改写 runtime 的指令文件"，换成"Fabric 绝不碰 SOUL/Memory/Skill/Session"。 |
| provider-native loading / file tools / approval / session / skills | Hermes 原生同名能力 | **REUSE（不复制）** | P0008.4 已确认，本 Audit 再确认：任何一个都不可复制。 |

**一个必须写清的映射结论**：agentFabric 的 workspace-root `AGENTS.md` 在 Claudian 体系里**同时对应两条轨道**——它既要有 Track B 的 orientation（"我在哪、这是什么、怎么导航、什么能改"），又要有 Track A 的 routing/scope 索引（"什么时候用哪个 context、每个 scope 的治理规则在哪"）。Claudian 用两个机制（system prompt + AGENTS.md）分开这两件事，agentFabric 只有一个文件可用，所以**这个文件必须显式分层，不能把 orientation、routing、navigation、content 混成一坨**（对应任务 Critical Semantic Separation）。

## 3. P0008.5 Failure Interpretation（Instruction Architecture 视角）

### 3.1 问题重述

> 为什么 `knowledge/` 能被 Blank Agent 消费，而 `systems/`（world/）大部分情况不主动消费？

不是"AGENTS.md 少了一句话"。从五个维度看，`knowledge/` 有一条**完整且对称的消费链**，`world/` 只有**生产侧（构建）链、没有消费侧链**。

### 3.2 五维分解

**① Orientation（我在哪 / 这是关于什么的）**

- `knowledge/`：任务本身就是知识任务（"整理共享知识""营销案例"），agent 的 orientation 天然指向 knowledge。
- `world/`：workspace 没有任何一句话把 agent 锚定到"这个 world 描述的是 **京东商智 + 祁门红茶官方旗舰店** 这个具体系统"。所以 Blank Agent 对"店铺星级"反问"哪家店铺"——它不知道这个 workspace 的 world model 就是关于一家具体店铺的。**Orientation 缺的是 subject anchoring（主题锚定）**。

**② Routing（什么情况下用哪种 context）** —— 缺失最严重

- `knowledge/`：有 task-triggered routing。AGENTS.md line 66-68："When ingesting … read `knowledge/KNOWLEDGE.md`"。KNOWLEDGE.md 内部又有 "Operations: Query → read INDEX → navigate"。
- `world/`：只有 **WRITE-side routing**。AGENTS.md line 72-75："When constructing `world/` … read `contracts/WORLD_MODEL.md`"。**没有 READ-side routing**——没有任何规则回答"当我被问到一个关于这个外部系统的事实问题时，我该先读 `world/` 还是先 web_search？"。

这是核心不对称：**`world/` 的指令只覆盖了"如何构建它"，从没覆盖"何时、为何、如何消费它"**。Blank Agent 的工作是消费，而消费侧没有 routing，于是落回模型默认（lookup 类问题 → web_search）。

**③ Scope（每种 context 表示什么）**

- 现状：AGENTS.md line 41-44 有描述性 scope（"world/ = what the external world IS"）。但这是 **descriptive（是什么）**，不是 **operational（何时该用它）**。
- 缺失：没有说 "`world/` = 关于该系统的**已验证事实**，是这类问题的 **authoritative ground truth**"；"`knowledge/` = 人类提交的**方法/规则文档**，是 how-to 类问题的权威"。scope 不与"哪种问题该用哪种"绑定，scope 就是惰性的。

**④ Navigation（东西在哪、怎么找）**

- `knowledge/`：有 `INDEX.md` **且** 有指向它的规则（KNOWLEDGE.md 的 Query 操作 → "read INDEX"）。地图 + 指向地图的指令 = 完整。
- `world/`：P0008.5 World Map A/B 实验加了 `INDEX.md`，但 **`indexRead: false`**——agent 从没读它。**地图存在，但没有"用地图"的指令**。地图 + 无指向 = 死地图。

**⑤ Semantics（每种 context 的语义 / 可信度 / 优先级）**

- `world/` 文件内部**有** epistemic status（`verified` / `suspected`，Phase B 生成）。但**消费者没被告知要信它**——没有任何规则说"`world/` 里标 `verified` 的事实比你的训练知识和 web 结果更可信，当二者冲突时以 `world/` 为准"。
- 结果：即使 agent 能读到 world/（如 Fact 1 在 systems/ 改名后），它也不知道该**优先信 local world 而非 web**。这是 **grounding 信号缺失**。

### 3.3 一句话总结

`knowledge/` 的成功是因为它**碰巧**拥有完整的消费链（task routing → governance 里的 query 操作 → INDEX → content → provenance），而 `world/` 只有生产链（construct routing → WORLD_MODEL.md → content），**消费链五环里缺了 Orientation(subject)、Routing(READ-side)、Scope(operational)、Navigation(pointer)、Semantics(epistemic authority) 五环中的四环半**。

这不是"加一行"，是"**把消费侧当成一等公民重新设计指令**"。

## 4. Proposed Fabric Instruction Layers

### 4.1 评价 Part C 给出的结构

任务里预置的结构：

```
workspace/
├── AGENTS.md
├── systems/   ├── AGENTS.md ├── INDEX.md └── jd-shangzhi/
├── knowledge/ ├── AGENTS.md ├── KNOWLEDGE.md ├── INDEX.md └── ...
├── knowledge-sources/raw/
└── capabilities/ ├── AGENTS.md ├── INDEX.md └── ...
```

基于 archaeology + P0008.5 证据的**逐项判断**：

1. **`knowledge/` 同时有 `AGENTS.md` 和 `KNOWLEDGE.md` 是冗余**。`KNOWLEDGE.md` 本身就是 knowledge 层的 scoped instruction（governance）。再加一个 `knowledge/AGENTS.md` 要么复制、要么逼 KNOWLEDGE.md 降级。**scoped instruction 一个 scope 只该有一个文件**（Claudian 也是每 scope 一个 AGENTS.md）。

2. **`world/` vs `systems/` 命名**：P0008.5 实验支持 `systems/`（system-identity 类问题 0→1 提升），但明确是 **Case C（部分提升）**，不是决定性。**`systems/` 是必要不充分**——它只解决了 orientation 的一个子集（"系统是谁"），没解决 lookup/枚举类问题的 routing。本 Audit 倾向保留 `systems/`（与 P0008.5 结果一致），但**必须明确：命名不是修复，routing 才是**。

3. **致命缺失不是结构，是两层内容**：
   - **Routing 规则**（READ-side：什么时候用 systems / knowledge / capability / web）
   - **Epistemic Semantics**（systems = verified ground truth，优先级高于 web 和训练知识）

4. **`capabilities/`（任务原文）vs 现状 `capability/`（单数）**：现状 AGENTS.md 写 `capabilities/`、实际目录是 `capability/`——**命名漂移**，证明缺少 canonical topology 定义。

### 4.2 提议的层次（保持 Critical Semantic Separation）

**不是"再加文件"，而是把五种语义显式分成五层，并补上缺失的 Routing + Epistemic Semantics：**

```
workspace/
├── AGENTS.md                 # L1 Instruction（root）：orientation + routing + 指向各 scope
├── systems/                  # L3 Content（Fabric 生成，READ-ONLY）
```

### 4.3 五层语义与归属（核心）

| 层 | 语义 | 载体 | 谁拥有 |
|----|------|------|--------|
| **Instruction** | Agent 在此环境中"如何工作"（orientation + routing + scope 触发规则） | root `AGENTS.md` + 各 scope 的 governance 文件 | Fabric |
| **Navigation** | "东西在哪、怎么找"（地图，不含答案） | 各 scope 的 `INDEX.md` | Fabric |
| **Content** | "具体知道什么"（world facts / shared knowledge / raw provenance） | `systems/*.md`、`knowledge/*.md`、`knowledge-sources/raw/*` | Fabric |
| **Capability** | "connected system 能做什么"（可观测什么） | `capability/bindings.md` | Fabric |
| **Runtime Self** | SOUL / Memory / Skill / Session / Plan / tools / approval | `HERMES_HOME`（**不在 workspace**） | Runtime |

**这条五层表是本次 Audit 的落点**：Instruction 与 Navigation 与 Content 分开（不混成大 Markdown），Capability 单独一层（不与 Content 混），Runtime Self 彻底排除在 workspace 之外。

## 6. Operational Capability Classification

P0008.5 已验证的四个行为，判定它们该"持久化"成什么，避免"测试时 agent 会、正式启动后不知道"。

| 行为 | 判定 | 持久化载体 | 为什么不是别的 |
|------|------|-----------|----------------|
| **System Context Construction**（Phase B：exploration artifact → structured world/） | **Fabric Procedure** | 一个 discoverable 的构建程序文档（现散落在 `contracts/WORLD_MODEL.md` 的引用里，且该引用已 dangling） | 不是 Capability（它不绑定 connected system，只操作 Fabric 自己的 context）；不是 Runtime Skill（Fabric-owned，非 runtime-owned）；不是 Instruction（instruction 讲规则，procedure 讲步骤流程）。 |
| **Shared Knowledge Ingestion**（Phase C/D：raw doc → 语义编译 → knowledge/ + provenance + INDEX + log） | **Fabric Procedure** | `knowledge/KNOWLEDGE.md` 已基本是此程序（governance + operations） | 同上。KNOWLEDGE.md 已经是"程序文档"，无需新造引擎，只需补 routing 指针让它 discoverable。 |
| **Context Navigation**（找到正确 context source） | **Workspace Instruction + Navigation** | root AGENTS.md 的 routing 规则 + 各 scope INDEX.md | 不是 Capability（不是 connected system 能力）；不是 Procedure（导航是"规则 + 地图"，不是多步工作流）；不是 Skill（导航 = agent 用原生 file tools 照着规则走）。 |
| **Grounded Context Consumption**（用 systems/knowledge 回答而非 web） | **Workspace Instruction**（outcome） | root AGENTS.md 的 Routing + Epistemic Authority 规则 | 这是**正确 instruction 的产物**，不是独立机制。它的"持久化"= 把 routing + epistemic 规则写进 instruction，让任何新 runtime 都读到。 |

**关键区分**（任务最担心的一点）：

- **Fabric Capability** = "connected system 能做什么"（如 `capability/bindings.md` 里的 `jd_metric_gmv observable_by trade.overview`）。四个行为里**没有一个是 Capability**——它们都是"agent 操作 workspace 自身 context"，不是"调用 connected system"。
- **Runtime Skill** = Hermes 的 skill（可复用、带 version/owner/confidence 的运行时能力）。四个行为**也没有一个是 Skill**——把"构建 world"做成 Hermes skill 反而违反 ownership（那是 Fabric 的程序，不是 runtime 的能力）。
- 所以结论：**这四个行为属于 Instruction + Navigation + Procedure 三层，全部 Fabric-owned，全部可以（也必须）以纯 Markdown 文件持久化在 workspace 内**。它们不会"正式启动后 agent 不知道"，前提是它们从测试报告落成 workspace 文件，且 root AGENTS.md 有 routing 指向它们。

## 7. Open Questions / Risks

1. **scoped instruction 的命名**：统一 `AGENTS.md`（Claudian 风格，signal 强但泛化）还是描述性名（`KNOWLEDGE.md` / `GOVERNANCE.md` / `WORLD_MODEL.md`，自解释但 signal 弱）？这影响 Hermes 是否原生加载 nested AGENTS.md（Hermes 只加载 cwd root，nested 需指向）。**本 Audit 建议**：scoped 文件统一一个约定命名（推荐保留描述性名 + root 里 routing 指向），但这是 P0008.6 Proposal 要定的事。

2. **`contracts/WORLD_MODEL.md` 是 dangling reference**（`data/fabric-workspace/AGENTS.md:73` 引用，但 repo 内不存在 `contracts/` 或 `WORLD_MODEL.md`）。P0008.2 的 World Model Contract 只存在于 proposal，从未落成 workspace 内可被 runtime 读到的文件。**这是"构建侧指令也没真正持久化"的证据**。

3. **命名漂移**：`capabilities/`（AGENTS.md）vs `capability/`（目录）；`world/`（AGENTS.md）vs `systems/`（实验结论）。生产 workspace 与测试 workspace 已经分叉（`data/fabric-workspace/world/jd_shangzhi/{system,features,assertions,...}.md` 与 P0008.5 测试目录结构不同）。**需要一个 canonical topology 定义 + 一次对齐**，否则 Instruction Architecture 建立后仍会再次漂移。

4. **Routing 的副作用风险**："systems 优先、web 兜底"这条 routing 会不会反过来伤害真实业务？例如 world/ 内容不全时（P0008.5 Probe A 的 Content Gap），强制"先 systems"可能导致 agent 硬答一个 world 里没有的答案。**Routing 必须配 "systems 无答案 → 明确 fallback web" 的退出条件**，不能变成"永远别用 web"。

5. **Epistemic Authority 的信任边界**：`verified` / `suspected` 由 Preparation Agent 在构建时标注（Phase B）。这个标注本身可能是错的。让 consumer 无条件信任 `verified`，等于把 preparation 的错误放大。**需要一个 provenance 链（哪个 artifact 支撑了哪个 assertion），而不是只有一档 `verified` 标签**。

6. **本 Audit 未回答的问题**：P0008.6 正式 Proposal 是否要走"先修 root AGENTS.md 的 routing/epistemic + 补 WORLD_MODEL 落盘 + 对齐 topology，再重跑 P0008.5 的 3 个 known-fact probe"作为验收？还是先只定义 ownership/representation、不做任何 workspace 文件修改？本 Audit 按任务要求**只定义，不改任何文件**——这是 Review 要拍板的下一步。
