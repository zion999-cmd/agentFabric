# P0007.2 — Legacy Intervention Semantic Mapping

**Type**: Fossil analysis — mapping old code structures to new Grammar hypothesis
**Date**: 2026-08-12
**Purpose**: Before designing the Human Intervention Grammar, understand what human behaviors the legacy code actually captured.

---

## 1. Grammar Hypothesis (v1)

```
Human Intervention
├── Response        — reacting to Agent/Signal/Situation output
├── Correction      — fixing the system's understanding of reality
├── Context Supplement — adding information the system can't observe
├── Decision        — deciding to act / not act / defer
└── Action Intent   — intending to change the real world

Action Intent
     ↓
Professional Action
     ↓
Action Execution
     ↓
World Change
```

## 2. Fossil #1: `ReviewAction` — approve / reject / modify

### Schema
```typescript
// shared/schemas/review.ts:11
ReviewActionSchema = z.enum(['approve', 'reject', 'modify'])
```

### What does each action actually carry?

**approve**:
```typescript
{ action: 'approve', reason: '...', reason_category: 'growth_legitimate' }
```
→ Agent said X, human agrees. **Maps to: Decision (accept)**

**reject**:
```typescript
{ action: 'reject', reason: '促销末期数据虚高', reason_category: 'promotion_ending' }
```
→ Agent said X, human disagrees + gives reason. **Maps to: Decision (reject) + Response (explaining why)**

**modify**:
```typescript
{
  action: 'modify',
  reason: '...',
  reason_category: 'manual_override',
  modified_output: Record<string, unknown>  // ← THE FOSSIL
}
```
→ Agent said X, human changes it to Y. **This is the richest fossil. Let's dissect it.**

## 3. Fossil #2: `modified_output` — What's Inside?

### Schema
```typescript
// shared/schemas/review.ts:66
human_action: z.object({
  type: ReviewActionSchema,
  modified_output: z.record(z.string(), z.unknown()),
})
```

### Construction site
```typescript
// apps/ecommerce/review/feedback.ts:17
modifiedOutput: input.modifiedOutput ?? {},
```

### What it captures (from ranking context):
When an operator rejects a ranking recommendation, `modified_output` can contain:
- Changed rank position ("this product should be #3, not #1")
- Changed signal weights ("promotion signal is overstated, reduce weight")
- Removed products from ranking
- Added products to ranking
- Changed confidence threshold

**This is NOT just "modify" — it's multiple distinct human behaviors:**

| What operator actually did | Legacy encoding | New Grammar |
|---|---|---|
| Demoted product from #1 to #3 | `modified_output: { rank: 3 }` | Correction (ranking) |
| Flagged promotion signal as unreliable | `modified_output: { signal_weights: {promotion: 0.1} }` | Correction (signal) |
| Removed product (seasonal item) | `modified_output: { excluded: ['sku_123'] }` | Context Supplement + Decision |
| Manually set product as #1 (business priority) | `modified_output: { override_rank: 1 }` | Decision (manual override) |
| Changed nothing but added a note | `reason: 'supplier called...'` | Context Supplement |
| Marked as "defer to next week" | No schema support at all | Decision (defer) — **invisible in legacy** |

## 4. Fossil #3: `reason_category` — What Did Operators Actually Say?

### Schema
```typescript
// shared/schemas/review.ts:17-28
'inventory_concern' | 'promotion_ending' | 'creator_drop' |
'seasonal_fluctuation' | 'market_trend_shift' | 'pricing_issue' |
'data_quality_doubt' | 'growth_legitimate' | 'manual_override' | 'other'
```

### Semantic analysis of each category:

| Category | What it really means | Grammar mapping |
|----------|---------------------|-----------------|
| `inventory_concern` | "System doesn't know we're low on stock" | Context Supplement (unobservable fact) |
| `promotion_ending` | "The data is right but it won't last" | Correction (temporal context) |
| `creator_drop` | "External factor the system missed" | Context Supplement |
| `seasonal_fluctuation` | "Normal pattern, not anomaly" | Correction (interpretation) |
| `market_trend_shift` | "Industry context missing" | Context Supplement |
| `pricing_issue` | "Data reflects price, not value" | Correction |
| `data_quality_doubt` | "I don't trust this metric" | Correction (signal reliability) |
| `growth_legitimate` | "Agent was right, this is real growth" | Decision (accept) |
| `manual_override` | "I'm making a business decision here" | Decision (override) |
| `other` | Catch-all | — |

**Pattern**: The 10 categories encode only TWO types of human behavior:
1. **Correction** (categories 1-7): "The system's model of reality is wrong"
2. **Decision** (categories 8-9): "I'm making a choice the system shouldn't make"

They DON'T capture:
- Action Intent ("I'm going to change the price")
- Professional Action ("I changed the price")
- Annotation ("Let me label this for future reference")

## 5. Fossil #4: `Feedback` — The Pre-P0007.4 Outcome Model

### Schema
```typescript
// shared/schemas/review.ts:58-76
FeedbackSchema:
  human_action: { type, modified_output }
  business_result: {
    metric_delta: Record<string, number>    // e.g. { gmv: +520 }
    attribution_window: '3d' | '7d' | '14d'
    baseline: Record<string, number>         // e.g. { gmv: 337 }
    post_value: Record<string, number>       // e.g. { gmv: 857 }
    signal_usefulness: Record<string, 'useful'|'mixed'|'not_useful'>
  }
```

### What it captures:
- ✅ Links human action → business outcome
- ✅ Has baseline/post_value (pre-cursor to P0007.4 Outcome)
- ✅ Has per-signal usefulness labels

### What it assumes (problematic):
- ⚠️ Human manually enters metric_delta (P0007.4 wants auto-observation)
- ⚠️ Human self-attributes causality
- ⚠️ No link to re-observation evidence

### Grammar mapping:
| Feedback field | New Grammar |
|---------------|-------------|
| `human_action.type: 'modify'` | Correction or Decision |
| `business_result.metric_delta` | Outcome (P0007.4 — needs auto-observation) |
| `business_result.signal_usefulness` | Response (per-signal evaluation) |
| `business_result.baseline/post_value` | Outcome snapshot (P0007.4) |

## 9. What the Fossils Tell Us

### The 10 `reason_category` types collapse into 2 Grammar types:

All 7 "correction-like" categories (`inventory_concern` through `data_quality_doubt`) are the same human behavior: **"The system's model of reality is incomplete or wrong."** They differ only in what domain knowledge is missing (inventory, promotion, seasonality, etc.) — but the intervention type is the same: **Correction**.

The 2 "decision-like" categories (`growth_legitimate`, `manual_override`) are: **"I am making a choice."**

### `modified_output` contains at least 4 distinct behaviors:

1. **Correction (ranking)** — changed rank position
2. **Correction (signal)** — changed signal weights
3. **Context Supplement** — added unobservable information
4. **Decision (manual override)** — business priority overrides algorithm

### The Grammar is simpler than we thought:

Not 10 categories × 3 actions = 30 combinations. More like:

```
Response     ← approve, reject+reason, signal_usefulness labels
Correction   ← modify (ranking), modify (signal), 7 reason_categories
Context      ← modify (add note), modify (exclude seasonal)
Decision     ← approve, reject, manual_override, (defer — new)
```

## 10. Recommendation for P0007.2 Contract

The v1 Grammar hypothesis holds up against the fossil record. The minimal Intervention schema should be:

```typescript
HumanIntervention:
  type: 'response' | 'correction' | 'context_supplement' | 'decision' | 'action_intent'

  // For 'response': what are you responding to?
  respondsTo: { agentActivityId?, signalId?, observationId? }

  // For 'correction': what understanding is wrong?
  corrects: { observationId?, signalId?, metricName? }

  // For 'context_supplement': what unobservable fact?
  supplements: { observationId?, situationAspect: string }

  // For 'decision': what's decided?
  decision: { accept?, reject?, defer?, override?, noAction? }

  // For 'action_intent': what are you about to do?
  actionIntent: { description, target, expectedEffect? }
```

The detailed schema (exact Zod shapes, optionality, cross-references) is P0007.2 implementation. This fossil analysis confirms: the old code's 10 categories + 3 actions compress cleanly into 5 intervention types, and the `modified_output` unstructured blob contains behaviors that the new Grammar can finally give proper structure.
