# P0009.1: Situation Producer / Today’s Work

**Status**: Proposed
**Date**: 2026-08-16
**Depends on**: P0007, P0008.6, P0009

## Objective

建立缺失的 **Situation Producer**，把已经存在的 `Evidence → Signals → Rankings` 转换成真实、可解释、可持久化的 `Situation`，使 Workspace「今日工作」第一次拥有真实业务内容。

本阶段不是建设新的分析系统，而是把已有经营认知结果提升为**“当前值得关注的经营事项”**。

第一版必须保持确定性、可解释、可去重；**不使用 LLM 判断什么值得关注**。

---

## Background

当前真实链路已经能够工作：

```text
JD 商智
  ↓
Evidence Store
  ↓
Signals
  ↓
Rankings
  ↓
[ GAP ]
  ↓
Situation
  ↓
Workspace「今日工作」
```

P0007 已经存在：

* `SituationSchema`
* `LearningContextSchema`
* `determineLifecycle`
* `isLearnable`
* `POST /api/situations`
* Situation persistence
* `situation-viewmodel.ts`

但代码审计确认：

> **不存在 canonical Situation Producer。**

当前 `situations` 表为空，不是 UI 或 backfill wiring 问题，而是系统从未实现：

```text
Signals / Rankings
        ↓
“什么现在值得关注？”
        ↓
Situation
```

P0009 已经让 Workspace、Hermes、Capabilities、Evidence 和真实 JD 数据开始进入产品表面。

P0009.1 补齐的就是**机器经营状态 → 人/Agent 工作对象**这一层。

---

## Architecture

```text
              Existing Data Runtime
                      │
             Evidence / Signals
                      │
                  Rankings
                      │
                      ▼
          ┌─────────────────────┐
          │ Situation Producer  │   ← NEW
          │                     │
          │ detect              │
          │ explain             │
          │ deduplicate         │
          └──────────┬──────────┘
                     │
                     ▼
              SituationSchema
                     │
                     ▼
             situations table
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
     Workspace             Hermes / Agent
    「今日工作」             Situation Context
```

Situation 是一个 **business attention object**。

它不是 Signal 的复制，也不是任务（Task），而是：

> 根据当前已有经营证据，系统认为值得被进一步关注、分析或处理的一个业务情境。

---

# Design

## 1. Producer 输入

Producer 只消费已经存在的 canonical runtime outputs：

```text
Signals
Rankings
```

必要时允许引用对应 Evidence provenance，但**不得重新采集 JD 数据**。

Producer 不直接调用：

```text
JD CDP
Hermes
LLM
MCP
web_search
```

因此：

```text
JD acquisition
      ↓
Evidence
      ↓
Signals
      ↓
Rankings
      ↓
Situation Producer
```

职责严格单向。

---

## 2. 第一版 Situation Detection

P0009.1 不试图定义完整的“经营智能”。

只建立最小、确定性的 Situation detection。

第一版从当前已有数据中检测三类 Situation：

### A. Meaningful Change

某经营指标出现已有 Signal 所表达的明显变化。

例如：

```text
访客数明显下降
转化率改善
成交金额持续增长
```

Producer **消费 Signal 已有的 direction / value / metrics / observedAt**，不重新计算业务指标。

---

### B. Ranking Attention

Ranking 已经表明某商品值得关注。

例如：

```text
商品排名明显上升
商品排名明显下降
高潜商品进入前列
```

Producer 消费现有 Ranking 结果。

不得重新实现 Ranking Engine。

---

### C. Cross-signal Attention

当同一 entity / 时间窗口存在多个已有 Signal 时，可以生成一个组合 Situation。

例如：

```text
流量下降
+
转化率上升

→

“流量下降但转化改善，值得检查流量来源变化。”
```

第一版只允许**简单确定性组合规则**。

不得调用 LLM 做开放式归因。

---

## 3. Situation 内容

生成结果必须符合现有 `SituationSchema`。

核心语义至少包括：

```text
situation_id
type
description
entity
temporal
```

同时应保留能够追溯来源的引用。

概念上：

```text
Situation
 ├─ what happened
 ├─ affected entity
 ├─ observed time
 └─ source references
       ├─ signal
       └─ ranking
```

如果现有 Schema 没有 source reference 字段：

**优先复用已有 P0007 可表达结构。**

不要为了 P0009.1 顺手重构 Situation Schema。

只有确实无法表达最小 provenance 时，才允许做最小 contract extension。

---

## 4. Deterministic Description

第一版 description 使用模板生成。

例如概念上：

```text
{entity} 的 {metric} 较近期基准出现明显下降。
```

或者：

```text
{product} 的经营排名明显上升，进入当前值得关注的商品集合。
```

要求：

* 来自真实 Signal / Ranking；
* 数值存在时可以包含数值；
* 不虚构原因；
* 不生成“建议增加投放”等行动建议；
* 不把 observation 写成 causal conclusion。

Situation 描述的是：

> **发生了什么。**

而不是：

> **为什么发生 / 应该怎么办。**

后两者属于 Agent / 专业人员后续工作。

---

## 5. Dedup Identity

必须解决当前 `situations` 表没有语义 dedup 的问题。

第一版使用 deterministic identity。

建议概念：

```text
situation_key =
  type
  + entity
  + subject/metric
  + observation_window
```

例如：

```text
meaningful_change
product:sku_123
traffic.uv
2026-08-16
```

同一个 observation window 内重复运行 Producer：

```text
第一次 → CREATE
第二次 → SKIP / UPDATE existing
```

绝不能：

```text
服务重启 10 次
→ 今日工作出现 10 条相同 Situation
```

具体 hash/ID 实现由 Claude 按现有项目规范决定。

---

## 6. Lifecycle

复用 P0007 已存在的：

```text
determineLifecycle
isLearnable
```

不要重新设计 Situation lifecycle。

Producer 的职责只到：

```text
detect
→ construct
→ persist
```

后续 Situation 如何：

```text
open
partial
mature
```

继续遵守 P0007 contract。

---

## 7. Startup Wiring

当前已经存在：

```text
backfillRecentData()
  ↓
Evidence
  ↓
Signals
  ↓
Rankings
```

P0009.1 在其完成后接入 Producer：

```text
startup
   ↓
backfillRecentData
   ↓
Signals / Rankings ready
   ↓
SituationProducer.run(...)
   ↓
situations persisted
   ↓
Workspace「今日工作」
```

Producer 必须消费**已经完成的本地结果**。

不得因为 Situation generation 再触发 acquisition。

---

## 8. Workspace Consumption

Workspace 已经存在 Situation presentation path。

P0009.1 只要求：

```text
Situation Producer
      ↓
existing situations persistence/API
      ↓
existing Situation ViewModel
      ↓
「今日工作」
```

如果前端因为真实字段与旧 fixture 有轻微 wiring gap，可以做最小修正。

**不要重新设计「今日工作」页面。**

最终页面至少应该真实出现类似：

```text
今日工作

• 店铺访客数出现明显下降
  流量 · 今日

• 商品 A 排名明显上升
  商品 · 今日

• 转化率改善但流量下降
  经营 · 今日
```

内容必须来自当前数据库真实 Signals / Rankings。

# Boundaries

## Included

* 新增 canonical `SituationProducer`。
* 从已有 Signals / Rankings 检测最小 Situation。
* deterministic Situation description。
* deterministic dedup identity。
* 复用 P0007 Situation persistence/lifecycle。
* 接到当前 startup backfill 完成之后。
* 让 Workspace「今日工作」展示真实 Situation。
* 增加 Producer 单元测试。
* 做一次真实 Workspace acceptance。

---

## NOT Included (CRITICAL)

### 不建立新的分析引擎

不要新增：

* Situation AI analyzer
* anomaly engine
* recommendation engine
* reasoning engine
* scoring platform

Signal Engine / Ranking Engine 已经存在。

Producer **消费它们，不重建它们。**

### 不使用 LLM 生成 Situation

本阶段：

```text
NO Hermes
NO OpenAI
NO DeepSeek
NO Agnes
NO Nemotron
```

参与 Situation detection。

这是 deterministic runtime capability。

### 不生成 Action / Task

不要实现：

```text
Situation → Task
Situation → Action
Situation → Workflow
Situation → 自动执行
```

Situation 只是 attention object。

### 不实现专业人员工作流

本阶段不做：

* assign
* owner
* claim
* resolve
* comment
* approval
* collaboration
* notification

专业人员能够**看到什么值得关注**即可。

他们如何处理，是后续阶段。

### 不修改 Acquisition

不要修改：

* JD CDP
* local-first acquire
* Evidence Store
* startup 7-day backfill 策略

Situation Producer 不允许触发 CDP。

### 不修改 Capability Execution

不要修改：

* Fabric MCP
* CapabilityRegistry
* CapabilityBinding
* `/api/fabric/execute`
* Hermes tool discovery
* AGENTS capability execution semantics

P0009.1 与 Agent capability execution 是两条独立链。

### 不解决模型稳定性

不要继续实验：

* `agnes-2.5-flash`
* `agnes-2.5-pro`
* Nemotron
* DeepSeek
* tool_search 配置
* prompt tuning

### 不重构 P0007

P0007 contract 能复用就复用。

不要因为 Producer 缺失而重新设计整个 Learning Context。

### 不做 Situation 自学习

不要让系统现在学习：

> “什么 Situation 对专业人员更有价值”。

未来专业人员的：

```text
关注
忽略
分析
纠正
行动
结果
```

才会成为 Situation Producer 演化的依据。

P0009.1 只建立这个未来闭环的**第一个真实观察点**。

# Success Criteria

1. **真实产生 Situation**
   使用当前数据库已有 Signals / Rankings 运行 Producer 后，`situations` 不再是 0 行，并且每条 Situation 可以追溯到真实 runtime output。

2. **Deterministic**
   相同输入重复执行 Producer，不产生重复 Situation。

3. **No Acquisition**
   Situation generation 全程不触发 JD CDP；已有 Evidence/Signals/Rankings 足够时，CDP invocation count 必须为 0。

4. **No LLM**
   Producer 执行过程中没有 Hermes/LLM 调用。

5. **Startup Closed Loop**
   服务启动后：

```text
backfill
→ signals
→ rankings
→ situations
```

自动完成，不需要 CLI/manual POST situation。

6. **Workspace Visible**
   从真实 Workspace 页面进入「今日工作」，能够看到本次生成的真实 Situation，而不是 fixture/demo/静态内容。

7. **Grounded Content**
   抽查至少 3 条 Situation，其 entity / metric / direction / timestamp 与对应 Signal 或 Ranking 一致。

8. **P0007 Lifecycle Reuse**
   Situation 使用现有 P0007 lifecycle semantics，不产生第二套 lifecycle。

9. **Existing Runtime Regression**
   P0009 已跑通的以下能力不得因本阶段退化：

```text
Readiness
Capability Explorer
Evidence Viewer
Agent Session canonical route
Fabric execution boundary
local-first Evidence
```

10. **Final Browser Acceptance**
    最终验收必须从 Workspace 浏览器页面观察：

```text
JD persisted data
   ↓
Signals / Rankings
   ↓
Situation Producer
   ↓
situations persistence
   ↓
Workspace「今日工作」
```

给出 **PASS / PARTIAL / FAIL**。失败时停在真实断点，不用 fixture/mock/manual POST 补链。
