# P0008.6 — Fabric Workspace Instruction & Exposure Architecture

**Date**: 2026-08-14
**Depends on**: P0008.2 (World Model Contract), P0008.3 (Agent Workspace & Runtime Integration), P0008.4 (Shared Knowledge Layer), P0008.5 (Bootstrap E2E)
**Supporting audits**: `audits/p0008.6-claudian-instruction-architecture.md`, `audits/p0008-operational-capability-exposure.md`
**Type**: Architecture Proposal — no implementation

---

## 1. Objective

让 **Situation Chat → Hermes Session → Fabric Workspace** 成为 P0008 的 canonical Runtime Path，并让一个正式启动的 Blank Runtime（无 JD Soul/Skill/Memory、无测试专用 prompt）能够发现和使用 Fabric 已经拥有/验证的：

- System Context（`systems/`）
- Shared Knowledge（`knowledge/`）
- Capabilities（`capabilities/`）
- Validated Procedures（`procedures/`）
- Context Instructions / Navigation（`AGENTS.md` + 各 scope `INDEX.md`）

两个 Audit 已经证明：**问题不是单一 Instruction Gap，而是 production exposure architecture 尚未收敛。** 本 Proposal 收敛它。

---

## 2. Problem（从两个 Audit 提炼）

1. **两条断开的生产 Runtime 路径**：P0008.3 的 session 路径（`/api/situation/:id/chat`）与 Phase 3 的 legacy 路径（`/api/chat` + CapabilityBridge）没有桥接。CapabilityRegistry(11) 只在 legacy 路径可见，session runtime 只看到 `capability/bindings.md`(1)。

2. **Topology 未锁定**：`world/` vs `systems/`、`capability/` vs `capabilities/` 同时存在于代码与实验，且焊死在 code 里；生产 `data/fabric-workspace` 与 P0008.5 实验 workspace 已分叉；`contracts/WORLD_MODEL.md` 是 dangling reference。

3. **World/System 消费失败**：P0008.5 已知 0/3（systems/ 改名后 1/3）。根因是 `systems/` 只有 WRITE-side 指令（构建）、无 READ-side 指令（消费）——缺 Routing + Epistemic Semantics + Navigation 指针。

4. **Procedure 只有测试行为**：System Context Construction 在 P0008.5 靠 test prompt 让 Preparation Agent 执行；生产里 projector 用 code 代劳，Agent 无此路径，且无任何持久 asset 告诉 Runtime 这个 Procedure 存在。

5. **持久化被破坏**：`writeProjection` 每次启动 `rmSync(workspace)`，Agent 编译进 `knowledge/` 的内容重启即丢，违反 P0008.4 "persistent knowledge" 原则。

## 3. Canonical Runtime Path

```
Situation Chat (Workspace UI)
        ↓ POST /api/situation/:id/chat
Situation Chat Bridge (platform/server/routes/situation-chat.ts)
        ↓ session.create(cwd = canonical workspace, profile = …)
Hermes Session (cwd → filesystem-native discovery)
        ↓ read AGENTS.md → route → INDEX → content/capability/procedure
Fabric Workspace
```

**这是 P0008 唯一的 canonical runtime path。**

Legacy `/api/chat → Hermes oneShot → CapabilityBridge` 状态：

- **不删除**（保持 Phase 3 既有功能）。
- **冻结职责**：不再承载任何新的 P0008 能力。
- 未来 P0008 能力（capability/procedure 暴露、system context 消费）只走 canonical session 路径。

CapabilityBridge 不删除，但它在 P0008 语境下的角色被重新定义为：**CapabilityRegistry 的 code-level authoritative reader**（供 CapabilityProjector 读取），不再是 runtime 直接调用的 path。

## 4. Canonical Workspace Topology

锁定为：

```
workspace/
├── AGENTS.md                    # root instruction（Hermes 原生加载）
├── README.md                    # human-facing orientation（最小）
├── systems/                     # System Context（Fabric 生成，READ-ONLY）
│   └── jd-shangzhi/             # ← systemId（kebab-case）
│       ├── INDEX.md             # navigation（系统列表 + "什么问题去哪找"）
│       ├── system.md            # System（店铺是谁/星级/导航模块数…）
│       ├── surfaces.md          # Surfaces
│       ├── features.md          # Features (Affordances)
│       ├── metrics.md           # Metrics
│       ├── dimensions.md        # Dimensions
│       ├── constraints.md       # Constraints
│       └── assertions.md        # Assertions（含 epistemic status）
├── knowledge/                   # Shared Knowledge（Agent-maintained，PERSISTENT）
│   ├── KNOWLEDGE.md             # governance / 维护规则（不是业务知识）
│   ├── INDEX.md                 # navigation
│   ├── log.md                   # append-only maintenance log
│   └── <topic>/…                # compiled knowledge pages
├── knowledge-sources/           # immutable provenance（PERSISTENT）
│   └── raw/                     # 人类/外部提交的源材料（只读）
├── capabilities/                # Runtime-facing Capability projection（生成，READ-ONLY）
│   ├── INDEX.md                 # navigation（11 capabilities + domain 分组）
│   └── <capability-id>.md       # per-capability card
└── procedures/                  # Runtime-facing Procedure definitions（生成，READ-ONLY）
    ├── INDEX.md                 # navigation（有哪些 procedure）
    ├── system-context-construction.md
    └── shared-knowledge-ingestion.md
```

**解决的 drift**：

| 现状问题 | 锁定后 |
|---------|--------|
| `world/` vs `systems/` | **`systems/`**（P0008.5 实验：system-identity 类问题 0→1） |
| `capability/` vs `capabilities/` | **`capabilities/`**（与 AGENTS_CONTRACT 已写的复数一致，且是 catalog 语义） |
| `jd_shangzhi` vs `jd-shangzhi` | **`jd-shangzhi/`**（kebab-case，与 P0008.5 一致） |
| `contracts/WORLD_MODEL.md` dangling | **删除该引用**。World Model 结构折叠进 `procedures/system-context-construction.md`（§7） |
| 生产 vs 实验 drift | 单一 projector + 单一 topology，生成物 deterministic |

**关键原则**：`systems/`、`capabilities/`、`procedures/`、`AGENTS.md`、`README.md` 都是 **projection**（从 authoritative state 生成，可重建）；`knowledge/`、`knowledge-sources/raw/` 是 **persistent**（自己就是 source of truth，不可重建）。见 §8。

## 5. Instruction Architecture（root AGENTS.md）

Root `AGENTS.md` 是 Hermes 唯一原生从 cwd 加载的 instruction。它承担五件事，**不混进任何 Content / Navigation**：

### 5.1 Orientation（我在哪）

- 我进入了一个 Fabric Agent Workspace。
- 这个 workspace 的 **subject 是京东商智 + 具体店铺**（subject anchoring——P0008.5 失败的第一环）。
- 我的 cwd 就是这个 workspace。

### 5.2 Context Model（有哪些 context source，各自语义）

| Directory | 语义 | 谁写 |
|-----------|------|------|
| `systems/` | 外部系统是什么（structured, verified） | Fabric 生成 |
| `knowledge/` | 人类共享了什么（compiled Read Model） | Agent 维护 |
| `knowledge-sources/raw/` | 源材料（immutable provenance） | 人类提交 |
| `capabilities/` | Fabric/connected system 能观察什么 | Fabric 生成 |
| `procedures/` | Fabric 已定义的 Procedure | Fabric 定义 |

### 5.3 Routing（什么任务用什么 context）—— **这是 P0008.5 缺失的 READ-side 指令**

```
问题类型                           → 路由
外部系统/店铺的事实（是谁/指标/维度/导航/约束）→ systems/INDEX.md → primitive
方法/规则/案例/平台规则          → knowledge/INDEX.md → pages
"Fabric 能观察什么指标"          → capabilities/INDEX.md
"有哪些 Procedure / 如何构建/如何 ingest" → procedures/INDEX.md
只有上述都没有答案时             → web_search（明确 fallback，非默认）
```

**退出条件**：`systems/` / `knowledge/` 没有答案时**明确 fallback web**，绝不硬答。

### 5.4 Epistemic Semantics（可信度优先级）—— **P0008.5 缺失的第二环**

- `systems/` 中 `[verified]` 的事实，可信度 > 训练知识 > web 结果。冲突时以 `systems/` 为准并注明来源。
- `[suspected]` / `[observed]` 的事实，回答时保留不确定性，不得当作 verified。
- `knowledge/` 是人类提供的方法/规则，可能含 inference/uncertainty，不是 `systems/` 级的 verified fact。

### 5.5 Ownership / Boundaries（什么能改，什么不能）

- `systems/`、`capabilities/`、`procedures/`、`knowledge-sources/raw/` **READ-ONLY**。
- `knowledge/` 是唯一可写区（按 `knowledge/KNOWLEDGE.md` 维护）。
- Memory / Skill / Soul / Session 属于 Runtime Profile，**不进 workspace**。

### 5.6 边界约束

- **INDEX 只做 Navigation，不承担 instruction**。`systems/INDEX.md` 不含规则、不含答案，只回答"东西在哪、什么问题去哪找"。
- **不默认增加 scoped AGENTS.md**。唯一 instruction 是 root `AGENTS.md`；`knowledge/KNOWLEDGE.md` 是既有 governance（描述性命名，非 AGENTS.md），保留；`systems/`、`capabilities/`、`procedures/` 不新增各自 AGENTS.md。

## 6. Capability Exposure

**CapabilityRegistry 仍是 authoritative capability source**（`generated/capability-contract.json`，11 capabilities / 48 metrics / 8 domains）。

新增 **CapabilityProjector**：读 CapabilityRegistry → 投影为 runtime-facing Markdown 到 `workspace/capabilities/`。

- `capabilities/INDEX.md`：列出全部 11 capabilities，按 domain 分组（navigation）。
- `capabilities/<capability-id>.md`：每个 capability 一张 card（name / capability id / domain / 观察什么指标 / acquisition / outputs）。

**关键约束**：

1. **投影，不复制、不重新定义**。card 内容来自 CapabilityRegistry 的 contract 字段，projector 只做格式转换（JSON → Markdown），不新增 capability 语义。
2. **取代 `capability/bindings.md`(1)**。旧的单条 binding 投影被 capabilities/ catalog 取代——它曾是"11 vs 1"脱节的根源。Capability Binding（World Object ↔ capability 的 relationship）仍存在，但作为 `systems/assertions.md` 里的 `observable_by` assertion + capability card 里的 `observes` 字段呈现，不单独设一个只含 1 条的文件。
3. CapabilityRegistry 与 workspace **同源**：projector 每次启动从 authoritative registry 重建 capabilities/，drift 不可能发生。

## 7. Procedure Exposure

将 P0008.5 已实验验证的两个行为，定义为 **Fabric-owned Procedure**：

| Procedure | 已验证证据 | 触发 | 产物 |
|-----------|-----------|------|------|
| **System Context Construction** | P0008.5 Phase B（Exploration Artifact → structured world/） | 有新的 World Exploration Artifact，需要构建/更新 `systems/` | 更新 `systems/` |
| **Shared Knowledge Ingestion** | P0008.5 Phase C/D（raw doc → semantic compilation → knowledge/） | 有新的 raw source 提交到 `knowledge-sources/raw/` | 更新 `knowledge/` |

**`procedures/<name>.md` 每份表达**（declarative，非可执行代码）：

```
# <Procedure Name>
## Goal             —— 这个 procedure 完成什么
## Trigger          —— 什么条件下应该执行它
## Inputs           —— 读什么（源/契约文件）
## Steps            —— 步骤（Agent 用自身 reasoning + file tools 执行）
## Outputs          —— 写到哪
## Contract         —— 结构契约（如 World Model 6 primitives + assertions + epistemic status）
## Ownership        —— Fabric-owned；Agent 执行；不写 Hermes Skill
```

**关键边界**（四重区分）：

- **Procedure ≠ Capability**。Capability = connected system 能观察什么（`capabilities/`）；Procedure = Agent 执行的多步工作方法（`procedures/`）。
- **Procedure ≠ Hermes Skill**。Skill 是 Runtime-owned（version/owner/confidence/retirement）；Procedure 是 Fabric-owned 的 declarative 文档，由任何 Runtime 读并执行。
- **Procedure ≠ test prompt**。它不是"开发测试时给 Agent 的 prompt"，而是 workspace 内的持久 asset，任何 Runtime 通过 `procedures/INDEX.md` 可发现。
- **不建 Workflow Engine**。本阶段只 productize 已有 evidence 的两个 Procedure；`procedures/*.md` 是文档，无调度/执行引擎。

**`contracts/WORLD_MODEL.md` 的去向**：World Model 结构契约（6 primitives + assertion + epistemic）是 System Context Construction 的 Contract，折叠进 `procedures/system-context-construction.md` 的 `## Contract` 段。root AGENTS.md 不再引用不存在的 `contracts/WORLD_MODEL.md`，改为 routing 指向 `procedures/INDEX.md`。

## 8. Persistent Knowledge Ownership

**问题**：`writeProjection` 的 `rmSync(workspace, recursive)` 把 Agent 编译进 `knowledge/` 的内容连同投影一起清空。

**修复原则**：把 workspace 目录**按 source-of-truth 性质分成两类**，分别用不同策略：

| 目录 | Source of Truth | 策略 | 重启后 |
|------|-----------------|------|--------|
| `AGENTS.md` / `README.md` / `systems/` / `capabilities/` / `procedures/` | authoritative state（code constants + WorldModel + CapabilityRegistry） | **project / regenerate**（清空重建） | 重建，不丢 |
| `knowledge/` / `knowledge-sources/raw/` | **它们自己**（Agent 维护的知识、人类提交的 provenance） | **ensure / seed if absent**（幂等，不覆盖） | 保留 |

**实现拆分为两个 operation**（替代当前的 `writeProjection` + `initSharedKnowledgeLayer` 顺序）：

```
ensureWorkspace(dir):
  1. projectRegenerable(dir)     # 只清空并重建 systems/ capabilities/ procedures/ AGENTS.md README.md
  2. ensurePersistent(dir)       # 幂等 seed knowledge/ + knowledge-sources/raw/（若缺失才创建，绝不覆盖已有页面）
```

**关键约束**：

- `projectRegenerable` **绝不 `rmSync(workspace 根)`**，只对 regenerable 子目录逐个清空。
- `ensurePersistent` 对 `knowledge/` **只 seed 结构 + 首次 seed 页面**；对 Agent 已生成的页面**永不覆盖、永不删除**。
- **source of truth / write-back ownership**：Agent 写 `knowledge/` 就是写 source of truth（knowledge 自己就是 authoritative Read Model，无 write-back 需要）；`systems/`、`capabilities/`、`procedures/` 是 projection，Agent 的写**永不**反向写回 authoritative state（投影单向）。

**不建**：数据库、同步引擎、git-based versioning。本阶段只用 filesystem 语义（regenerable vs persistent）解决问题。

## 9. Ownership Boundaries（Fabric vs Runtime）

| 类别 | Fabric-owned | Runtime-owned（Hermes / Claude Code / …） |
|------|--------------|-------------------------------------------|
| Workspace topology | ✅ | — |
| root AGENTS.md + governance | ✅ | — |
| `systems/`（生成 + 内容） | ✅ | — |
| `knowledge/`（治理 + 持久） | ✅ | — |
| `capabilities/`（投影） | ✅ | — |
| `procedures/`（定义） | ✅ | — |
| INDEX 导航 | ✅ | — |
| SOUL / Memory / Skills | — | ✅ |
| Sessions / Plans | — | ✅ |
| file tools / approval | — | ✅ |
| instruction loading | 提供文件（放对位置） | ✅ 原生从 cwd 加载 |

三条铁律（继承自 Claudian archaeology + P0008.4）：

1. Fabric **绝不**创建/注入/改写 Runtime 的 SOUL / Memory / Skill / Session。
2. Fabric 的"只读"是 **Instruction Policy**，不是安全机制；enforcement 是 Runtime 的 approval/permission，Fabric 不重实现。
3. Procedure 是 Fabric 的 declarative 文档，**不写入 Hermes Skill**。

### 断言（每个都要有 filesystem/tool evidence）

| # | 断言 | 证据 |
|---|------|------|
| A1 | Agent 发现本地 JD system context | `read_file` / `search_files` 命中 `systems/` |
| A2 | 正确回答 P0008.5 三个 known-fact probes（星级 4.6 / 行业对比基准 / 导航模块 10） | 答案正确 + `read_file` 证据（非 web_search） |

## 12. Implementation Breakdown（高层，非代码）

1. **Topology 收敛**：改 `AGENTS_CONTRACT`（`world/`→`systems/`、`capabilities/`→`capabilities/`、删 dangling `contracts/WORLD_MODEL.md`）、`projector.ts`（写 `systems/` + `systems/INDEX.md`、`capabilities/` 目录、kebab-case systemId）。

2. **Persistence 修复**：拆分 `ensureWorkspace` → `projectRegenerable` + `ensurePersistent`；`writeProjection` 不再 `rmSync` workspace 根。

3. **CapabilityProjector**（新）：读 CapabilityRegistry → 写 `capabilities/INDEX.md` + per-capability cards。

4. **ProcedureProjector**（新，或并入 shared-knowledge 的 constant 模式）：写 `procedures/INDEX.md` + 两个 procedure 文档（含 World Model Contract 折叠进 construction procedure）。

5. **fixture enrichment**：`JD_FIXTURE` 增加 P0008.5 已提取的三个 known-fact（system 属性 + dimension）。

6. **Acceptance**：复用 P0008.5 的 Blank Hermes 探针方法，重跑三个 known-fact + 新增 capability/procedure/persistence 断言。

## 13. Open Questions（供 Review）

1. **`knowledge-sources/raw/` 位置**：保留在 workspace root（当前设计）还是移入 `knowledge/` 下？P0008.5 已验证"root 唯一、不嵌套"的 invariant 有效，倾向保留 root。但"persistent provenance" 与 "agent-maintained knowledge" 是两类持久资产，是否需要显式分目录强调？

2. **Capability card 粒度**：每 capability 一个文件 vs 单个 catalog 文件？本 Proposal 倾向 per-capability（可扩展、与 knowledge 模式对称），但对 11 capabilities 是否过度？实现时可定。

3. **`systems/INDEX.md` 是否由 projector 生成还是 agent 维护**：本 Proposal 定为 projector 生成（因为 systems/ 是投影、只读）。但 P0008.5 里 INDEX 由 Preparation Agent 生成。生成职责变更是否影响 navigation 质量？

4. **`situation/` 是否进入 topology**：projector 有可选 `situation` 输入（P0007），但生产未接线。本 Proposal 不纳入 P0008.6 范围，留 P0007。
