# P0007.1 Audit — Learning Context Contract

**Commit**: 4664210
**Files**: `shared/schemas/learning-context.ts`, `tests/contract/learning-context.contract.ts`
**Audit type**: Read-only schema review — no code changes

---

## 1. Runtime-Neutral ✅

**PASS** — Schema contains no Hermes-specific fields.

Evidence:
- `AgentActivityRef.agentRuntime` is `z.string().default('hermes')` — free-form string, not enum
- Test `runtime-neutral` explicitly asserts no `hermesMemory`, `hermesSkill`, `chainOfThought` keys
- No Hermes-internal identifiers in any schema field

**Minor concern**: `default('hermes')` is a convenience default, not a constraint. If future runtimes use a different agentRuntime string, the schema works. The default value is fine — it's a helper, not a lock-in.

---

## 2. Situation/Case as First-Class Anchor ✅

**PASS** — `situationId` is the root anchor, distinct from `contextId`.

Evidence:
- `SituationSchema` has its own `situationId` (independent identity)
- Type system: `situation.type` enum covers 6 business scenario types
- Entity + temporal scope bound to Situation, not to Context
- Description is a required human-readable field

The Situation IS a business anchor, not a renamed taskId. A taskId (`AgentActivityRef.taskId`) is an optional cross-reference, not the primary key.

---

## 3. Object References vs Data Duplication ⚠️

**WARNING** — Partial data duplication in `metrics` and `summary`.

Evidence:
- ✅ `ObservationRef.evidenceIds` — true ID reference
- ✅ `ObservationRef.signalIds` — true ID reference
- ✅ `ActionRef.interventionId` — true ID reference
- ✅ `OutcomeRef.actionId` — true ID reference
- ⚠️ `ObservationRef.metrics` (`Record<string, number>`) — **duplicates metric values**
- ⚠️ `ObservationRef.summary` (string) — **duplicates evidence description**
- ⚠️ `OutcomeRef.baseline/postValue` (`Record<string, number>`) — **duplicates metric snapshots**

The `metrics` and `baseline/postValue` fields copy actual data values into the Learning Context. This means:
1. If the source evidence/signal changes, the Context is stale
2. The Context grows with data, not just references
3. These fields are convenient for Runtime consumption but violate "reference by ID" principle

**Design tradeoff**: Runtime learning needs metric snapshots to work without re-fetching all evidence. The convenience may be worth the duplication. But the duplication should be explicit: mark these as `// snapshot — source of truth is evidence[sig]`.

---

## 4. Partial Context Validity ✅

**PASS** — Missing Intervention/Action/Outcome is explicitly valid.

Evidence:
- All three arrays default to `[]`
- `isLearnable()` only requires `observations.length > 0 && agentActivities.length > 0`
- `determineLifecycle()` gracefully handles: open (no intervention/action/outcome) → partial (has intervention or action) → mature (has outcome)
- Test `minimal (open lifecycle)` validates a context with NO interventions, actions, or outcomes

The contract correctly handles partial data.

---

## 5. Incremental Enrichment ✅

**PASS** — Context can be enriched without recreation.

Evidence:
- Test `incremental enrichment` validates: open → add intervention → partial → add action+outcome → mature
- Lifecycle is dynamically determined, not fixed at creation
- All enrichment arrays are additive (push semantics) without needing to recreate the root object

A Context can start with just Situation + Observation + Agent Activity. Intervention, Action, and Outcome are added later as they occur.

---

## 6. Provenance — Reference Graph or Decoration? ⚠️

**WARNING** — Mixed: real reference graph woven through fields, but `provenance` top-level object is a summary.

Evidence:

**Real reference graph** (in main fields):
- `ObservationRef.evidenceIds[]` → evidence files
- `ObservationRef.signalIds[]` → signals
- `AgentActivityRef.taskId` → execution task
- `HumanIntervention.reviewId` → feedback record
- `HumanIntervention.actionId` → triggered action
- `ActionRef.interventionId` → triggering intervention
- `OutcomeRef.actionId` → parent action
- `OutcomeRef.evidenceIds[]` → outcome evidence

**Decoration** (in `provenance` object):
- `capabilitiesUsed: string[]` — aggregated list, not linked to specific observations
- `agentRuntimes: string[]` — aggregated list
- `humanActors: string[]` — aggregated list
- `totalEvidence: number` — count, not reference
- `totalSignals: number` — count, not reference

The `provenance` field is a convenience summary. The real provenance is in the cross-reference ID chains above.

**Recommendation**: Rename `provenance` → `summary` or `stats`. The word "provenance" suggests the reference graph, but this IS a summary. The true provenance IS there — it's just not called provenance.

## 7. Premature Implementation of Later Sub-Proposals ⚠️

**WARNING** — P0007.2 (Action Grammar) and P0007.4 (Outcome) are partially pre-implemented.

### P0007.2 — Human Intervention & Action Grammar

- ✅ `ActionRef` is **minimal**: `type: z.string().min(1)` — no Action Grammar, just a free-form label. Correct for P0007.1.
- ⚠️ `HumanIntervention` is **not minimal**: defines all 7 intervention types (`decision`, `correction`, `annotation`, `context_supplement`, `action_intent`, `no_action`, `other`). The P0007 Proposal says P0007.1 is the "minimal contract" and P0007.2 extends it. Having the full type enum in P0007.1 pre-implements part of 7.2.

**Assessment**: The intervention type enum IS the grammar. It's reasonable to define it minimally in P0007.1 since you need to reference intervention types. But it IS pre-implementing P0007.2's type system.

### P0007.4 — Outcome Observation

- ⚠️ `OutcomeRef` has `baseline` + `postValue` + `observationWindow` — this IS the core outcome model
- The observation window enum (`3d/7d/14d/30d/custom`) pre-defines the re-observation pattern
- P0007.4 is designed to "establish Outcome Observation" — having the schema here pre-implements it

**Assessment**: Similar to intervention types — defining the structure minimal is necessary for reference. But `baseline/postValue/observationWindow` IS P0007.4's scope.

### P0007.5 — Provenance & Trust

- ✅ No Trust model. No Verifiability Trust or Execution Reliability Trust schema exists. Correct for P0007.1.

## Recommendation

**KEEP with notes** — No blocking issues. Three warnings are design tradeoffs, not bugs:

1. **Data duplication (metrics/baseline)**: Acceptable tradeoff for Runtime convenience. Add `// snapshot` comments to mark them as derived.
2. **provenance vs summary**: Rename `provenance` field to `summary` or `stats`. The real provenance is the ID reference chains.
3. **Partial pre-implementation**: The intervention type enum and outcome model ARE P0007.2/7.4's scope, but defining minimal types now is acceptable for schema coherence. Don't add more 7.2/7.4 detail until those phases.
